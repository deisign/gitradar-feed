Основная модель строится вокруг трёх требований:

- inspectable — видно используемые модели, инструменты, версии, возможности и доступ к данным;
- traceable — действия агента можно связать с исходной задачей и цепочкой исполнения;

FIT:
Это хорошо ложится на архитектуру, где LLM не получает произвольный доступ к исполнительному слою.

Целевая схема:

agent proposal
→ semantic / allowlisted tool
→ policy validation
→ approval при необходимости
→ deterministic execution
→ trace / audit

Особенно релевантны runtime hooks, observability и возможность централизованно deny/modify действия агента.

PROJECT:
Agent Security / Governance.

Связан с Private AI, MCP tool layer и всеми системами, где агент способен совершать реальные действия.

NEXT:
Сравнить ACS control model с нашим planned MCP execution layer:

- semantic allowlisted tools;
- current/desired state validation;
- approval gates;
- audit trail;
- restricted capabilities;
- deterministic execution.

Не внедрять весь стандарт автоматически: сначала определить минимальный совместимый control envelope.

### kunchenguid/axi

URL: https://github.com/kunchenguid/axi
VERDICT: KEEP
SCORE: 31
STARS: 1871

WHAT:
AXI — Agent eXperience Interface: набор принципов для инструментов,
которыми пользуются прежде всего AI-агенты, а не люди.

Проект исходит из того, что обычные CLI и MCP часто создают лишний
контекст и лишние round trips.

Ключевые принципы:

- token-efficient output;
- минимальные default schemas;
- controlled truncation с явным full mode;
- pre-computed aggregates;
- однозначные empty states;
- structured errors и exit codes;
- non-interactive/idempotent mutations;
- contextual disclosure следующих действий.

Есть reference implementations для GitHub и browser automation.
Авторы также публикуют собственные benchmark'и AXI против обычного CLI
и MCP.

FIT:
Содержательно это не Design Systems tool, несмотря на автоматический bucket.

Для Lancelot AXI интересен как reference того, каким должен быть tool surface
после discovery/security слоя.

MCPProxy отвечает на вопросы:

- какие инструменты доступны;
- каким можно доверять;
- какой intent у вызова;
- нужно ли approval.

AXI отвечает на другой вопрос:

- как сам инструмент должен разговаривать с агентом, чтобы не жрать
  контекст и не требовать лишних turns.

Особенно полезны compact output, definitive empty state,
pre-computed aggregates и fail-loud errors.

PROJECT:
Lancelot / Agent Infrastructure.

Reference для tool UX и bounded execution surface.

NEXT:
Сделать небольшой architecture diff:

1. обычный `gh`;
2. GitHub MCP;
3. `gh-axi`.

На нескольких одинаковых задачах сравнить:

- количество tool calls / turns;
- объём возвращаемого контекста;
- качество error states;
- пригодность output для дальнейшего reasoning.

Отдельно определить, какие AXI principles стоит сделать требованиями
для собственных tools Lancelot.
